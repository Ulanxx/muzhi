# 第 6 期：Pi——极简派的一千 token 提示词与会话树

> **Harness 拆解课 · 第 6 期（共 10 期）**
>
> 前几期拆的都是"加法"：Codex 加补丁文法、Claude Code 加钩子、Gemini 加压缩流水线。这期拆"减法"。Pi 的核心系统提示词只有一段话，工具默认就四个，却敢做工业级产品。它把省下来的复杂度放哪了？答案在存储层：一个 append-only 的会话树。我们读穿这两处源码，把树移植进 mini-agent。

---

## 这期解决什么问题

- **提示词能有多短？** 我们 mini-agent 的系统提示越写越长，总怕模型不懂。Pi 用一段话做完了同样的事——它凭什么？
- **第 4 期遗留的另一半：** OpenCode 的 fork 是"复制出一条新会话"。同一个问题——走岔了想重来——Pi 给了一个完全不同的存储学答案。

---

## Step 1：拆提示词——一段话的自信

证据在 `packages/coding-agent/src/core/system-prompt.ts`（L121 起），剥掉动态拼装，核心就这么一段：

```text
You are an expert coding assistant operating inside pi, a coding agent harness.
You help users by reading files, executing commands, editing code, and writing new files.

Available tools:
- read: ...  - bash: ...  - edit: ...  - write: ...

Guidelines:
- Be concise in your responses
- Show file paths clearly when working with files
```

没有长篇行为规范，没有几十个"切记"。三个设计细节值得学：

**① 准则随工具集动态生成（L104）。** 只有一条硬编码的条件准则："有 bash 但没有 grep/find/ls 时，才告诉模型用 bash 做文件检索"。工具表里没有的能力，提示词提都不提——**不教模型用不存在的工具**。

**② 文档不塞进提示词，给路径让它按需读（L131-138）。** 关于 pi 自己的文档（扩展、主题、SDK……）只放文件路径加一句"用户问到 pi 本身时再读"。这是把上下文窗口当硬盘用：提示词只存索引，内容按需加载。

**③ 项目上下文外挂（L145-152）。** `<project_context>` 标签包着项目自己的指令文件——和第 3 期 Claude Code 的分层指令同一个思想，但 Pi 只做一层，够用就停。

---

## Step 2：拆会话树——branch() 是一行代码

证据在 `packages/coding-agent/src/core/session-manager.ts`。Pi 的会话不是线，是**一个 append-only 文件长成的一棵树**，全部机制围绕三个字段：每个 entry 有 `parentId`，管理器持有一个 `leafId` 指针。

**分叉就是移动指针**（L1360）：

```ts
branch(branchFromId: string): void {
  if (!this.byId.has(branchFromId)) throw new Error(...);
  this.leafId = branchFromId;   // 就这一行
}
```

对比第 4 期 OpenCode 的 fork：那边要 structuredClone 全部消息、重建 idMap、重写一切回指——40 行。Pi 这边零拷贝：**旧消息原地不动，下一次 append 自然挂在老节点下面，长出新枝。**

**取上下文就是从叶走到根**（`getBranch`，L1260）：沿 parentId 走到根再 reverse。发给 LLM 的永远是一条路径，树的其他枝丫静静躺在文件里。

**废弃路径留摘要**（`branchWithSummary`，L1381）：分叉时可以给被抛弃的那条路立一份 `branch_summary` entry。注入上下文时的前缀文案（`messages.ts` L12）写得很诚实：*"The following is a summary of a branch that this conversation came back from"*——"这段对话曾经从那里回来"。

**导出是抽路径**（`createBranchedSession`，L1413）：想把某条枝变成独立会话？从叶走到根抽出来写成新文件，顺手重链 parentId。

文件头的注释（L1298）是这一切的地基：**"The session is append-only... Entries cannot be modified or deleted."** 不可变历史（进阶篇第 6 期的 canonical 原则）在 Pi 这里不是设计品味，是存储格式本身。

## Step 3：造——session-tree.ts

移植进沙箱 99 行（`SessionTree`）：`append`（挂在当前叶下、叶前移）、`branch`（移指针）、`resetLeaf`（回到 null，下次 append 长新根——Pi 用它实现"重编辑第一条消息"）、`getPath`（叶到根走链）、`getLeaves`（没人指向的节点 = 活动分支的指尖）。一处适配：Pi 把 branch_summary 挂在分叉点旁、由上下文构建器拉入路径；我们直接让它当新分支的第一个节点——少一层机制，效果等价。

---

## 跑起来看看：废弃分支的教训活在新分支里

`demo-hns-06.ts` 的剧情：agent 帮忙决定"用户偏好存哪"。A 分支聊定了浏览器方案（localStorage），用户反悔；`branchWithSummary` 记下废弃理由回到分叉点，B 分支改聊服务端方案，最后追问"之前那条路为什么不走"：

```text
── 第一幕：A 分支（浏览器存储）──
  ├ agent：最关键的权衡点是数据安全与隐私：服务端存储更安全可控……浏览器存储则存在XSS攻击风险。
  ├ agent：用 `localStorage` 或 `IndexedDB` 存储键值对即可……

── 第三幕：B 分支（服务端存储）──
  ├ agent：用 Cookie 存用户ID，服务端数据库按ID记录偏好，前端通过API读写。
  ├ agent：因为浏览器存储无法实现跨设备同步，且清理缓存会丢失偏好设置。

── 验尸 ──
  ▶ entries=9（append-only，只涨不删），leaves=2
  ▶ A 分支原地活着：4 条消息，结局未变
  ▶ 废弃分支的教训进入新分支：✓（摘要起了作用）
```

B 分支的 agent 从没见过 A 分支的对话原文——它引用"跨设备同步、清缓存丢失"全靠那条摘要。**分叉丢掉的是消息，留下的应该是教训。**

## 这期学到了什么

| 机制 | Pi 的做法 | 可抄的心法 |
|---|---|---|
| 系统提示词 | 一段话 + 动态准则 + 文档给路径 | 提示词存索引，内容按需加载 |
| 准则生成 | 只为实际存在的工具写准则 | 不教模型用不存在的工具 |
| 分叉 | `leafId = fromId` 一行，零拷贝 | 指针式分支 vs 复制式 fork |
| 废弃路径 | branch_summary：留下的不是消息是教训 | 分叉前先想清楚带走什么 |
| 存储 | append-only，不可删改 | 不可变不是品味，是格式本身 |

关键心智模型：**复杂度守恒。** Pi 没有在提示词和框架层堆复杂度，而是把它沉进存储格式——树结构让"撤销/重试/平行探索"全都变成免费的指针操作。极简不是少做事，是把事做到一个别人反复做很多事的地方。

## 课后练习

1. OpenCode fork（复制式）vs Pi branch（指针式）：前者每个会话独立、存储自包含；后者省空间、但任何会话文件损坏会牵连所有分支。给 mini-agent 写个 `materialize(tree, leafId)` 把一条路径导出成独立的线性 SessionStore（抄 Pi 的 `createBranchedSession`），想想什么场景该导出。
2. Pi 的准则是"工具表驱动"的。检查我们 mini-agent 的 systemPrompt：有没有哪句话描述了一个本次 `tools` 参数里根本没给的工具？写一个 `buildMinimalPrompt(toolset)` 把这种话自动生成。
3. `getLeaves` 现在要扫全表。给 SessionTree 加一个 `childrenByParent` 索引（append 时维护），然后想想：UI 上要画这棵树，DFS 还是 BFS？分支按什么排序（Pi 的 `getTree` 用时间戳排子节点，见 session-manager.ts L1343）？
